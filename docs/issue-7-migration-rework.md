# Issue #7: исправление обновления до 0.6.1

Предыдущий CI не доказывал миграцию исторической установки: MigrationTest вручную создавал синтетическую v1, device workflow устанавливал текущий debug и текущий release.

## Первопричина

В истории одного applicationId `ru.bruce.dispatcherinbox` выпущены две несовместимые схемы с одним `user_version = 2`:

| Исходник | Версия приложения | Схема |
|---|---|---|
| `2c42012c9ba655f74699bf9b7928b5f75c20b006` | 0.5.0/code5 | Room v1: записи и вложения |
| `7f7dbc7c9bc39d69a65baa74a6f51f4ae813c10d` | 0.5.1/code6 | Room v2: дополнительно `inbox_items.durationMillis` |
| `87b95fe7a172d56702e48410febd7c7a2c601765` | 0.6.0/code6 | Room v2: нет `durationMillis`, добавлена `drive_checkpoints` |

При install-over 0.5.1 → 0.6.0 номер БД не меняется. SQLite не вызывает upgrade, Room проверяет identity hash и отказывает в открытии. Прежний MIGRATION_1_2 не мог исправить этот путь. Кроме того, удалённое из модели поле длительности несовместимо с настоящей исторической v2.

## Исправление

0.6.1/code7 использует Room v3. Прямые миграции 1 → 3 и 2 → 3 добавляют nullable `durationMillis`, если его нет, и создают `drive_checkpoints`, если таблицы нет. Старые длительности сохраняются в модели. SQL не удаляет, не переименовывает и не пересоздаёт старые таблицы, не переписывает записи и не меняет файлы. Room проверяет конечную схему транзакционно. Экспорт схемы включён для последующих изменений.

## Постоянная проверка

`scripts/upgrade/build-history.sh` получает точные исторические коммиты через отдельные worktree. В историческое приложение не вносятся изменения; добавляется только инструментальный тест для наполнения БД через исторический Room. Для 0.5.0 и 0.5.1 это восстановленные сборки старых версий, без утверждения о побайтовом совпадении с прежними публикациями. Для 0.6.0 release берётся настоящий опубликованный APK из CI `41385603930` (артефакт `13115586915`), сохранённый в постоянном предварительном выпуске `migration-fixtures-issue-7`. Перед установкой проверяется закреплённый SHA-256 `ad71d7586c356d902f426847afb02002e132cfb0795f5b5fd5a3fc5c2a19a6bd`. Публикуются APK, SHA-256, сертификат и исходный коммит каждой сборки.

На выделенном эмуляторе `scripts/upgrade/install-over.sh` выполняет для каждой истории:

1. Ставит старый debug и создаёт старым Room три записи (`queued`, `error`, `synced`), связанные вложения и оригинальный файл.
2. Ставит соответствующий подписанный старый release через `adb install -r` и запускает его.
3. Для исторической v2 дополнительно ставит 0.6.0 и требует реальный отказ `Room cannot verify the data integrity` в AndroidRuntime.
4. Ставит новый release через `adb install -r`, без очистки данных между версиями.
5. Инструментальный тест открывает именно установленную БД, проверяет тексты с пробелами/Unicode, даты, статусы, source, retryCount, lastError, remoteId, старую длительность, имя/MIME/размер/путь/контрольную сумму вложения и точные байты файла. Для 0.6.0 проверяется сохранность Drive checkpoint.
6. Запускает MainActivity и проверяет живой процесс; сохраняет журналы и установленную версию.

Очистка разрешена только между независимыми сценариями на выделенном эмуляторе. Сценарий с `adb uninstall` не предназначен для физического телефона или пользовательской установки.

## Ограничения

Физический Ulefone Android 14: штатный адаптер на Brain доступен, но `reconcile ulefone` вернул `AWAITING_DEVICE` (нет актуального ADB-объявления ожидаемого адреса). Физический install-over/launch — **NOT TESTED**. Настройки, аккаунты и личные данные не менялись. Drive/OAuth/Obsidian этим исправлением не расширяются. PR #8 не сливается.

Результаты CI, подпись и ссылка на APK фиксируются после завершения проверки в Issue #7 / PR #8.
